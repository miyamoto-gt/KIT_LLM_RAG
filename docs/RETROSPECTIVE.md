## 2. 仕組み（v-final6）

```
【事前（手元）】
  サイト巡回・本文抽出・手作りデータ → submission/knowledge/*.md（出典URL・確認日つき）

【実行時（main.py。本番は運営のサンドボックス、CPU のみ・30分）】
  起動：全問「不明」の CSV を先に書く
  資料：knowledge/*.md → 500字・重なり100字のチャンク（9132件）→ 文字2-gram の BM25
        資料の埋め込み →【運営 API】sarashina-embedding-v2-1b（約5分）
  1問ごと（6問並列）
    ① 振り分け：事実／説明／計算、答えの部分の数、出力の上限
    ② 質問を分ける：「AとBは、それぞれ〜」→ 1つずつ答えてつなぐ
    ③ 検索：埋め込みの上位40件＋BM25の上位40件 → RRF
            × 新しさの補正（過去を聞く質問では無し）→ 手作りデータを優先
            → 同じページは2件まで → 上位4件 → 前後のチャンクをつなぐ
    ④ 絞り込み：質問と関係する文（前後1文）を8文残す。箇条書き（①②…）は続きの項目も残す
    ⑤ 生成 →【運営 API】sarashina2.2-3b
       計算：質問が与えた数 → <calc> → 文中の式 → 数値を書き出させる、の順にコードで計算
    ⑥ 点検と直し（だめなときだけ1回 API を呼ぶ）
       ・答えの形：何号館・何階・何人・いつ・どこ など
       ・名前の数：「6学部をすべて挙げ」で名前が足りない
       ・拒否（「記載されていません」「回答することはできません」）→ 質問を緩めて探し直す
    ⑦ 後処理：資料番号・前置き・答え方の説明・言い訳の文・途中で切れた文を外す
    失敗・タイムアウト：資料の中で質問といちばん重なる文で答える（簡易回答）
  2周目：全問に答え終わって時間が残れば、生成に失敗した問題だけ答え直す
  25分で打ち切り：残りは BM25 だけで簡易回答 → CSV を書いて終了コード0
```

| 処理 | 場所 |
|---|---|
| 資料の読み込み・BM25・RRF・絞り込み・計算・点検・後処理・簡易回答 | 自分のコード（CPU） |
| 資料と質問の埋め込み、生成 | 運営の API（DGX の GPU） |

## 3. 効いたこと

| 何をしたか | なぜ | 効果 |
|---|---|---|
| **運営 API 版に作り直す** | サンドボックスに torch が無く、手元で sarashina を動かす作りでは Private が毎回「実行失敗」だった | Private が初めて実行できた |
| **25分で打ち切る作り**（締め切りに合わせた待ち時間、`max_retries=0`、`os._exit`） | 夜は API が混み、31問で35分かかった。openai ライブラリが裏で2回やり直していた | 時間切れで0点になることが無くなった |
| **資料の埋め込みは1つずつ順番に送る** | 同時に送ると 502 が出た（中身の問題ではなかった） | 埋め込みが安定 |
| **計算はコードでする**（<calc> → 文中の式 → 数値の書き出し） | instruct 版は <calc> の指示に従わない。「総額」の行まで足すことがあった | 計算の問題が安定して正解 |
| **形の点検と1回だけの直し**（repair.py） | 小さいモデルは「何号館」に号館を書かない、などの取りこぼしが多い | だめな問題だけ API を1回増やして直る |
| **質問を分ける**（「AとBは、それぞれ」） | まとめて聞くと片方しか答えない | q078 などが正解に |
| **拒否のときの探し直し** | 資料はあるのに「記載されていません」と答える | q083・q023 などが正解に |
| **データを足す**（薄いページの取り直し66・抜けていた区画69・手作り66件） | 失敗の一部は資料に答えが無いことが原因だった | my_new69 が 56 → 62 |
| **簡易回答の改善**（質問と重なる文を選ぶ、答えの形に加点、目次・表のかけらを下げる） | 前は資料の最初の文（パンくずや表のかけら）を返していた | 簡易回答の正解率 10/66 → 41/66 |
| **並列6** | 並列8だと1回ずつが遅くなり、タイムアウトが増えるだけ | 69問で 54/66（並列8）→ 62/66（並列6） |
| **2周目** | 全問を終えても時間が13分ほど余っていた | タイムアウトした3問を毎回答え直せた（v-final3 84.7 → v-final4 87.1） |
| **箇条書きの続きを残す** | 検索は合っていたのに、8文に絞るときに③④の項目が捨てられていた（q088・q064） | 両方正解に |
| **答えを1問ずつ読んで部分点を直す** | キーワード判定では全問正解でも、採点 AI は3点をつけていた（矛盾した計算、前置き、言い訳） | v-final5 88.7 → v-final6 91.1 |

## 4. 効かなかったこと

| 何をしたか | 結果 | 分かったこと |
|---|---|---|
| 並列8 | 生成の中央値 121秒、タイムアウト11件、54/66 | サーバーが混んでいると、並列を増やしても全体は速くならない |
| 2周目で並列8の弱点を補う | 本番（69問＋埋め込み5分）では時間が余らず、2周目が始まらない | 2周目は時間が余ったときの保険 |
| 質問の「（専願型）」などの語を含む資料を前に出す | 正しい資料を押し出して悪化（資料に答えあり 59 → 58） | 原因は検索ではなく絞り込みだった。言葉の一致だけでは正しい資料を選べない |
| プロンプトの言い回しの調整（mix） | 下がった | 元の言い回し（v9）に戻した |
| 絞り込みの文数を増やす（8 → 12） | 誤差の範囲 | 8 のまま |
| 埋め込みを ruri-v3 に戻す・比べる | 検索の数字は同等 | sarashina-embedding のまま（運営 API で使える既定） |
| 失敗したまとまりを分けて送り直す（埋め込み） | API の回数が増え、1日の上限（429）に達した | サーバー側のエラーは送り直さず打ち切る |

## 6. 方針

- Public の問題文・答えを、プロンプト・お手本・手作りデータに使わない。直しはどの質問にも効く仕組みだけ
- 直しを入れる前に、自作セット（my_new69）と言い換えセット（paraphrase_set）でも下がらないことを確かめる
- 比べるときは並列1（`--workers 1`）。混んでいる時間の結果は当てにしない（`python submit.py run ping` で確かめる）
- 仮想環境は uv（`.venv-submit`、Python 3.12）
